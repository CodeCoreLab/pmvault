3.3 离线编译的两个必踩陷阱（实测）

陷阱 1｜工具链版本必须 ≥ go.mod 的 go 声明

测试机 apt 装到 Go 1.22.2，而 go.mod 写 go 1.23，断网编译报： 
go: downloading go1.23 (linux/amd64)
go: download go1.23 for linux/amd64: toolchain not available
Go 1.21+ 的 GOTOOLCHAIN=auto 默认行为是自动下载更高版本工具链，断网即成死路。
即使加 GOTOOLCHAIN=local 也只是变成另一条错误： 
go: go.mod requires go >= 1.23 (running go 1.22.2; GOTOOLCHAIN=local)
解法：把 go.mod 的版本降到离线环境的工具链版本（实测降到 1.22 后通过）。
陷阱 2｜改 go.mod 后必须重建 vendor，否则一致性校验直接拒绝

手工把 go 1.23 改成 go 1.22 后编译报： 
go: inconsistent vendoring in /tmp/alb:
  github.com/dustin/go-humanize@v1.0.1: is marked as explicit in vendor/modules.txt,
  but not explicitly required in go.mod   （共 6 条同类）
根因：vendor/modules.txt 里有 11 个 ## explicit 标记（含传递依赖），与 go.mod 的 require 块必须严格对应。
解法：改完 go.mod 后在联网机器上重新 go mod tidy && go mod vendor，三者（go.mod / go.sum / vendor）必须出自同一次生成。
陷阱 3｜CRLF 会让 sed 修改 go.mod 静默失效
从 Windows 编辑过的 go.mod 带 CRLF，sed -i 's/^go 1.23$/go 1.22/' 因行尾 \r 匹配不上而什么都不改，且不报错。实测改用 perl -pe 's/^go 1\.\d+\s*$/go 1.22\n/' 才生效。

四、跨平台编译的兼容性与注意事项

4.1 Go 交叉编译的硬性边界

场景是否可行说明与实测
纯 Go 依赖零配置 CGO_ENABLED=0 GOOS=windows GOARCH=amd64 一条命令即可，产出静态链接 PE，只依赖 kernel32.dll
含 CGO 依赖需 mingw 需 CC=x86_64-w64-mingw32-gcc CGO_ENABLED=1；实测装上 mingw 后成功（CGO 与纯 Go 产物哈希不同，证明确实走了 C 链路）
Windows 专用 API不可跨编译 如 syscall.NewLazyDLL、golang.org/x/sys/windows —— 只能在 GOOS=windows 时编译，Linux 上 go build（不带 GOOS）会编译失败。本项目已用 //go:build windows 分离 platform_windows.go / platform_other.go
SQLite本项目免 CGO 用 modernc.org/sqlite（C 转译成 Go），无需 C 工具链。若换 mattn/go-sqlite3 则必须 CGO + mingw
GUI（WebView2）本项目遇阻 详见第五章坑 4

4.3 路径与编码类兼容问题（跨平台高频）

问题表现与处理
Windows 路径分隔符Go 的 filepath 自动适配；但传给 SQLite 的 DSN 必须用正斜杠（实测本机 file:C:\...\x.db 打不开，需 filepath.ToSlash）

bat 脚本编码cmd 执行前按当前代码页解析脚本文件，UTF-8 中文会被拆成非法字节、行尾字节被当命令（实测报 '的' is not recognized）。脚本存 GBK + 开头 chcp 65001 + 脚本内提示只用 ASCII
换行符bat 必须 CRLF；shell 脚本必须 LF（CRLF 的 .sh 会报 $'do\r' 语法错）
长路径解压Windows 上 unzip 解 Go 官方 zip 只出 2,964/13,261 文件，用 Python zipfile 才完整

七、推荐环境选择与潜在限制

推荐

方案 A：跳板机编译 + Windows 验证

最省事 · 已完整跑通 · 适合日常迭代

流程：跳板机拉依赖 → 交叉编译 → SFTP 回 Windows → 哈希校验 → 运行验证。

为什么：跳板机有公网、8 核、120 GB 空闲，Go/Rust/mingw 齐全；Windows 只承担验证，不装编译环境。

前置：Go 在 /opt/go；dl.google.com + goproxy.cn 可达。

限制：跳板机是共享生产机，编译目录要放 /tmp 或 /opt/lab，不要碰业务目录；GOCACHE 会占几百 MB。

方案 B：跳板机预热 + 测试机离线编译

适合内网/隔离交付 · 已验证可行

流程：跳板机 go mod vendor → 41.8 MB 包搬到测试机 → 测试机断网 -mod=vendor GOPROXY=off 编译 → 回 Windows 验证。

为什么：证明断网流水线可行，适合合规要求「构建不出内网」的场景。

前置：测试机需内网 apt 装 Go（实测 1.22.2）；go.mod 版本必须 ≤ 1.22。

限制：工具链版本被 apt 锁死在 1.22，用不上新语法/新 std API；go mod tidy 无法在离线机执行（改依赖必须回联网机重做 vendor）。

方案 C：本机 Windows 直接编译

调试最快 · 但不建议作为唯一流程

流程：本机装 Go 便携版 → 原生 go build → 直接运行。

为什么：改一行动代码就能跑，调试周期最短；对 Windows 专用 API（WebView2、注册表、剪贴板）支持最完整。

限制：本机目前无 Go；跨平台产物仍需 Linux 侧产出（如 linux/arm64 部署包），双轨会增加一致性维护成本。

建议的组合：A 为主 + C 为辅。
· 日常迭代用 C（本机快）或 A（跳板机），改动小、反馈快
· 出交付产物统一走 A，保证产物可复现、可校验
· 需要隔离构建（合规/无网）才上 B，并接受 1.22 版本天花板

7.2 一句话总结

编译放 Ubuntu，验证放 Windows，这条链路是通的，而且我已经完整跑过一遍——产物 9.27 MB、只依赖 kernel32.dll、四架构全部成功、传输哈希一致、Windows 上注册/加解密/备份全部正常。

真正需要盯住的不是「能不能编」，而是三个版本一致性问题：go.mod 的 go 版本 vs 工具链、go.mod vs vendor/modules.txt、以及 CRLF 让脚本改动静默失效。这三处任一不一致都会报出看似无关的错误。

另外必须记住一条否定结论：WebView2 的 Go 绑定在本机 150.x 运行时上不可用，如果你的目标是「真 GUI 窗口」，不要在这条路上继续投入。

验证方式：所有结论均在真实环境实测 —— 跳板机 example-jump-host（Ubuntu 24.04.4, Go 1.23.4, mingw 13, Rust 1.99.1）、测试机 example-test-host（Ubuntu 24.04.4, Go 1.22.2, 无公网）、本机 Windows 11（Go 1.23.4 便携版）。产物经 SFTP 传输并做 sha256 逐字节比对，Windows 侧实际执行并跑通完整业务链路。
未验证项：windows/arm64 未在真机运行（仅交叉编译成功）；未做代码签名与杀毒环境测试；跳板机编译并发性能未压测。
