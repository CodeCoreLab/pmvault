一、项目概览

一个单机自部署的 Web 密码保险箱：PHP + SQLite，无需安装、无第三方云依赖，把程序丢到任意支持 PHP 的站点目录即可运行。设计目标明确——「数据只在自己服务器上」，因此全部复杂度集中在本地加密与密钥管理，而非分布式、多租户或同步。

维度实际情况
形态单体 Web 应用：2 个入口页（index.php 登录/初始化、main.php 主界面）+ 8 个 API 端点 + 5 个类库文件
使用者模型单账户系统：Auth::register() 首行即判 COUNT(users) > 0 就拒绝（includes/auth.php:124-127），本质是「个人保险箱」而非团队密码库
运行要求PHP 7.0+（推荐 8.x）、PDO_SQLite、OpenSSL；sodium 扩展为可选增强项
数据落盘data/passwords.db（SQLite 单文件，当前 100 KB，实测为空库）+ data/backups/*.db
代码规模PHP 5,290 行 / JS 3,967 行 / CSS 3,442 行；最大单文件 assets/js/app.js（3,657 行）、main.php（1,085 行）
版本演进v1.0 基础 CRUD → v1.2 引入 CBC+HMAC 与主密钥 → v2.0 加密体系换代（GCM + Argon2id + 恢复密钥 + 一批高危漏洞修复）
一句话定位：这是一次「加密架构重构」的产物，而不是功能堆砌的产物。从 README 的更新日志可见，v2.0 的绝大部分工作是把 v1 的「PBKDF2 10,000 次 + 用户名派生固定 salt + CBC + 无版本号密文」整体迁移到「Argon2id + 随机 salt + GCM + 版本化密文」，并保证老数据不丢、老用户无感。这套「向前兼容 + 静默迁移 + 失败回滚」的组合，是这个项目最值得读的部分。

二、技术栈

层选型说明与取舍
后端语言PHP 原生（无框架）无 Composer、无 autoload、无路由库。每个 API 文件 = 一个 switch ($action) 分发器，require_once 手动引入类库。取舍：部署零门槛（任何共享主机可跑），代价是路由/参数校验/错误处理三类横切逻辑在每个端点重复。
数据存储SQLite 3（PDO）单文件、无服务进程、天然契合单用户。表结构由 Database::initTables() 在每次连接时幂等创建/迁移（CREATE TABLE IF NOT EXISTS + ALTER TABLE 包 try/catch），无需迁移工具。读写全部走 PDO 预处理语句。
密码学OpenSSL（AES-256-GCM / CBC）+ libsodium（Argon2id）+ 内置 hash_pbkdf2/password_hash不引第三方加密库，全部用 PHP 内置扩展。Security::bestKdfType() 运行时探测 sodium 是否存在，决定走 Argon2id 还是 PBKDF2-600k。
前端原生 ES2017+ / Fetch / 无框架app.js 手感类似「手写 SPA」：全局状态变量 + 命令式 DOM 渲染 + 事件委托。无虚拟 DOM、无打包器，浏览器直接执行。
样式纯 CSS + CSS 自定义属性双主题:root 定义 20 余个语义变量，[data-theme="dark"] 只覆盖颜色变量；组件样式一次编写，主题切换零成本（assets/css/style.css:5-40）。主题值持久化在 users.settings JSON 字段里，跨设备一致。
图标内联 SVG Sprite（<symbol> + <use>）实测 main.php 内置 101 个 symbol，分类图标库 67 个（另有 30 个 Logo 白名单），全部 currentColor 描边，随文字色与主题自动变色。README 记录此举替换 Font Awesome，减少约 190 KB 加载。
交互组件自研模态框系统（alert / confirm / prompt + toast）用 customAlert/customConfirm/customPrompt/customShowToast 全面替代浏览器原生弹窗，保证样式统一、可异步 await、可定制按钮文案（app.js:2621-2770）。
Web 服务器Nginx / Apache 双支持Apache 走 .htaccess（RewriteRule ^(includes|data|logs)/ - [F,L] + <FilesMatch \.(db|sqlite3)$> Deny）；Nginx 无法读 .htaccess，需手工加 location ~* ^/(data|includes|logs)(/|$) { return 404; } —— README 显式标注了这个坑。

值得注意的两个「零依赖」细节

  • 前端不引第三方 CDN：所有 JS/CSS 同源加载，配合 Content-Security-Policy: default-src 'self' 才能真正生效。若引 CDN，CSP 就必须开口子。
  • 无构建链：改完文件刷新即生效，代价是 app.js 长到 3,657 行、style.css 长到 3,442 行，且靠 ?v=2.1.8 手工维护缓存版本号（main.php:1083）——这是没有被工程化的一处明显欠债。

3.5 三条关键流程

①「双密码」解锁链：登录 ≠ 解密

1
登录：password_verify(登录密码, users.password_hash) → 通过后 session_regenerate_id(true) 换 ID（防会话固定）→ 写 $_SESSION['user_id']，不写主密钥（auth.php:95-102）
2
解锁：首次查看/复制密码时弹主密钥框 → verify_master_key → 先 password_verify(主密钥密码, master_key_password_hash) 验口令，再按库中 kdf_type/kdf_params/salt 重新派生 32 字节主密钥 → 存入 session 并回传前端（api/auth.php:216-277）
3
使用：main.php 加载后先打 check_master_key 静默恢复会话内已解锁的密钥 → 刷新页面无需重输（app.js:110-118）
4
解密：api/passwords.php?action=decrypt 接收前端传来的 master_key → Security::decrypt()（GCM 认证）→ 首次失败且提示「不同主密钥」时，前端自动作废内存密钥、重新弹框验证、重试一次（app.js:1165-1187）

这套设计把「身份认证」与「数据解密能力」彻底解耦：登录密码泄露 → 攻击者进得来但看不到密码；主密钥密码泄露 → 攻击者看得到但进不来（还需登录口令）。二者独立修改互不影响（auth.php:251-256）。

②主密钥轮换（全量重加密）

1
验旧主密钥密码 + 强度校验新密码
2
按旧 kdf_type/params/salt 派生旧密钥 → 强制自动备份，备份失败即中止（auth.php:393-395）
3
beginTransaction() → 用新随机 salt + 最优 KDF 派生新密钥 → 遍历 passwords（含回收站 is_deleted=1）与 password_history，逐条 decrypt(old) → encrypt(new) → 更新 users 的 hash/salt/kdf 参数 → commit()（auth.php:400-443）
4
任何一步抛错 → rollback() → 返回「数据已回滚保持原样」；成功则 $_SESSION['master_key'] = 新密钥，当前会话无缝衔接，无需重新解锁

③恢复密钥（找回账户）

1
生成：验主密钥密码 → 派生出当前主密钥 → 随机生成 32 字符（字母表剔除 ILO01，8 组×4，约 158 bit 熵）→ 用 PBKDF2(rk, 随机 salt, 600k) 派生的密钥加密主密钥存入 recovery_backup → 明文密钥仅返回一次（auth.php:498-540）
2
验证（登录页第一步）：解 recovery_backup 得到主密钥 → 成功即通过；用户不存在/未设恢复密钥时照做一次同成本哑运算再返回失败，防时序探测（auth.php:474-491）
3
重置：拿到旧主密钥 → 强制备份 → 事务内全量重加密（条目 + 历史）→ 更新登录口令哈希、主密钥口令哈希、KDF 参数，并用新主密钥刷新 recovery_backup → session_regenerate_id 后自动登录（auth.php:560-659）

本质是信封加密（key wrapping）：数据用主密钥加密，主密钥用恢复密钥加密。这样「改密码」只需重加密一把钥匙，不必重新设计数据层。

五、亮点总结

亮点 1｜双密码分离：把「身份」与「解密能力」拆成两把钥匙安全架构
做法：users 表同时存 password_hash（登录）与 master_key_password_hash（解密）。登录成功只拿到会话，主密钥必须再验一次才派生。
思路：单密码方案里，登录成功 = 同时掌握解密权，任何一处泄露即全盘失守。拆开后形成「知道口令 ①→进得来」「知道口令 ②→看得见」的双因子错位；两个口令独立修改、互不牵连（auth.php:251-256 明确注释「修改登录密码不影响主密钥」）。
代价与补救：多一次输入。作者用「一次登录只解锁一次 + 会话内静默恢复（check_master_key）+ 密钥失配自动重试」把摩擦压到最低。
亮点 2｜主密钥从不落库，只落「派生参数」——因此算法可迭代密钥管理
做法：库里只有 master_key_salt / kdf_type / kdf_params。每次验证口令时按这三个字段临时派生 32 字节密钥，用完存 session。
思路：这是把 KDF 参数当作数据来存，而不是写死在代码里。于是「升级算法」变成一次数据迁移而非换代：deriveKey() 读 kdf_type 决定走 Argon2id（sodium_crypto_pwhash，opslimit 2 / memlimit 64MB）还是 hash_pbkdf2(sha256, 600k)，还能识别「无 kdf_type」的旧账户并自动走 legacy PBKDF2 10,000 次（security.php:66-123）。同一份代码同时伺候三个世代的用户数据。
工程价值：新环境装 sodium 就自动升级到 Argon2id，不改一行代码（README 亦以此为卖点）。这是「配置即迁移路径」的典型应用。
亮点 3｜静默迁移：备份 → 事务 → 失败回滚，老数据零丢失兼容性设计
做法：用户「首次用旧体系验证主密钥」时触发 migrateMasterKey()：先 autoBackup()（失败就放弃本次迁移、下次再试）→ 事务内逐条 decrypt(旧) → encrypt(新) → 更新 KDF 参数 → commit；异常则 rollback 并继续使用旧密钥，功能不受影响（auth.php:278-343）。
思路：把「不可逆的加密升级」拆成「可重试的惰性操作」。三个安全阀很到位：迁移前必有备份（备份是前置条件，不是尽力而为）、全程单事务（不会出现一半新一半旧的中间态）、失败即降级（返回 null，调用方继续用旧 key，用户无感）。
同类一致：改主密钥密码、恢复账户两条流程复用了完全相同的「备份 → 事务 → 回滚」骨架，行为可预期。
亮点 4｜版本化密文 + 三格式自动识别 + 歧义回退密码学细节
做法：v3 格式 base64( 0x03 ‖ IV(12) ‖ Tag(16) ‖ Ciphertext )，首字节为版本号。decrypt() 读首字节构造候选列表（0x03→v3、0x02→v2、兜底 legacy），逐个尝试，前一个失败才试下一个（security.php:226-331）。
思路（这段注释值得抄）：旧版密文没有版本前缀，其首字节就是随机 IV 的第 0 字节，有 1/256 概率恰好等于 0x02 或 0x03。若只看首字节判定格式，约 0.8% 的老数据会被误判而永久解不开。作者的解法是「按可能性顺序全部试一遍」，靠 GCM/HMAC 的认证失败即拒绝来自证格式——用密码学完整性替代格式标记，正确且优雅。
同一血统：v2 用的是 AES-CBC + HMAC-SHA256 且严格 encrypt-then-MAC（先加密再对 iv‖ciphertext 做 HMAC），校验用 hash_equals() 常量时间比较——即便在旧格式上也没犯「MAC-then-encrypt」这个经典错误。
亮点 5｜恢复密钥 = 信封加密，且「仅显示一次」可用性 × 安全
做法：32 字符、剔除易混字符（无 I L O 0 1）、8×4 分组、约 158 bit 熵。用 PBKDF2(rk, 随机 salt, 600k) 派生包装密钥，加密主密钥后存库；明文只在生成响应里出现一次，前端用大字号展示框提示抄写（security.php:140-170、auth.php:498-540）。
思路：传统「安全问题找回」＝把安全等级降到最弱环节。这里换成「你能证明持有那张纸」：离线 + 一次性 + 高熵，攻击者只能靠暴力猜 158 bit，而服务端已限流到每小时 10 次（按用户名）/ 30 次（按 IP）。重新生成会让旧密钥立即失效（覆写 recovery_backup）。
闭环设计：账户找回成功后主动刷新 recovery_backup 为新主密钥（auth.php:632），所以同一张纸可以反复救急，不必每次换新。
亮点 6｜防时序侧信道：三处「假动作」做得认真攻击面收敛
做法 1：用户名不存在时，仍对一条硬编码 bcrypt 哈希执行 password_verify()，让「用户不存在」与「密码错误」耗时一致（auth.php:55-59）。
做法 2：恢复密钥验证对「用户不存在 / 未设置恢复密钥」场景照常执行完整 600k PBKDF2 派生，只在最后返回 null，并注释「哑运算已完成，耗时与真实场景一致」（auth.php:474-491）。
做法 3：getClientIP() 只信任 REMOTE_ADDR，显式拒绝 X-Forwarded-For，理由写在注释里：请求头可任意伪造，信任它等于让 IP 限流失效、日志被污染（security.php:459-467）。
为何值得记：绝大多数自研项目只在「密码比对」上小心翼翼，却漏掉「分支提前 return」泄露状态这一层；也常见「为了拿真实 IP 而信任 XFF」反而被打穿限流。这三点说明作者是真读过攻击面清单的。
亮点 7｜限流下沉到数据库：丢 Cookie 也绕不过去防护强度
做法：保留会话级 rateLimit() 但明确标注「不用于防爆破」，另实现 dbRateLimit(name, max, window) 以 rate_limits 表计数。登录双维度：login_ip_* 10 次/60s + login_user_* 5 次/300s；主密钥验证 mkverify_* 10 次/300s；改主密钥 5 次/300s；恢复密钥生成 5 次/3600s（security.php:416-457）。
思路：会话级限流的致命伤是「清 Cookie 即重置」，等于没有。改存 DB 后，计数器与攻击者身份解耦。作者还补了两个工程细节：并发插入冲突时 insert 失败降级为 update；按 random_int(1,100)===1 概率性清理过期记录，避免为清理单开定时任务。
容错取向：限流组件自身异常时放行（fail-open）而非拒绝——可用性优先，与「个人保险箱」的定位自洽。
亮点 8｜备份一致性：VACUUM INTO + 三重校验 + 还原前紧急备份数据可靠性
一致性：用 VACUUM INTO 'path' 而非 copy()——前者在数据库打开状态下生成事务一致的完整快照，后者可能拷到「主文件已写、WAL 未合并」的半成品。旧版 SQLite 才降级为「先 Database::close() 再 copy」（backend backup.php:71-88）。
完整性：verifyBackupIntegrity() 三重检查——非 0 字节 + PRAGMA quick_check == 'ok' + sqlite_master 中存在 users 表。第三条尤其关键：SQLite 会把 0 字节文件当作合法空库，若不拦，还原一个空备份 = 静默清空全部数据（api/backup.php:32-52）。
可回退：还原前先用同样方式给当前库拍紧急备份并校验，不通过就取消还原；紧急备份同样进列表管理、可再还原。还原后 Database::close() 重置单例，避免旧 PDO 句柄继续指向被替换的 inode 导致「还原后写入丢失」——这个坑在更新日志里被明确记为已修（api/backup.php:199-236）。
前端配合：还原是「确认框 + 输入『确认还原』二次确认」双保险，成功后提示「首次查看密码需重新输入主密钥」并 3 秒自动刷新（app.js:2516-2545）。
亮点 9｜前端零依赖的性能与体验取舍性能 / UX
减重：Font Awesome 全量替换为内联 SVG Sprite，README 记录减约 190 KB；图标统一 currentColor，深浅主题自动适配，无需两套资源。main.php 一次性内联 101 个 <symbol>（约等于一次 HTTP 请求拿完整个图标库）。
去装饰：更新日志明确写「移除遮罩层实时模糊」「移除全站装饰性动画」——backdrop-filter: blur() 在低端设备上是实打实的掉帧源，砍掉它换来弹窗即开即用。这是以体验指标（响应感）压过视觉指标（炫技）的清醒取舍。
健壮性：apiCall() 先 response.text() 再 JSON.parse()，并对「非 JSON 错误响应」「空响应」「损坏 JSON」分别给出人话提示，而不是让 fetch().json() 抛浏览器原始错误（app.js:62-105）。列表渲染用 createElement + textContent 构造，仅 URL 一处用 innerHTML 且经 escapeAttr 全转义，XSS 面控制得比较干净。
双视图：桌面 <table>、移动卡片，共用同一份 passwords 数组与同一套 CRUD 回调，不做两套数据流。
亮点 10｜导入导出「不经明文落盘」的巧思数据流动
做法：导出的 CSV 里密码列填的是密文 cipher，不是明文；模板则给明文示例。导入时用 isEncryptedCipher() 判断：合法密文直通入库（不重新加密），明文则用当前主密钥加密（api/import_export.php:37-51, 115-124）。
价值：导出是密码管理器最危险的出口——一个明文 CSV 留在下载目录就等于全盘泄露。这里让「备份到 CSV」在不降低安全等级的前提下可用（前提：导入时用同一主密钥，且该 CSV 只对本系统有意义）。导出还带 BOM 保证 Excel 中文不乱码，导入端主动跳 BOM、按表头定位密码列、兼容缺列文件。
幂等：以「同标题 + 同网址」为业务主键做 upsert，重复导入不会翻倍，且以导入数据为准覆盖字段。
亮点 11｜零迁移工具的「自愈式」建表可维护性
做法：initTables() 在每次连接时执行 CREATE TABLE IF NOT EXISTS，逐条 ALTER TABLE ADD COLUMN 包在 try/catch 里让「列已存在」的异常静默通过；同时用 PRAGMA table_info 探测旧字段决定是否补列（database.php:53-252）。
思路：把 schema 升级做成幂等的、随连接自动执行的动作，用户升级只需覆盖文件、刷新页面。对「无运维、无 CLI、上传即用」的分发形态来说，这比引入 Phinx/Doctrine Migrations 务实得多。数据目录与 index.html 占位文件也在 config.php 里自愈创建（config.php:65-78）。

六、局限与潜在改进点

下列问题按「是否影响数据安全/正确性」分级。P0 = 会丢数据或可被直接绕过；P1 = 功能实质失效或安全强度明显低于宣称；P2 = 工程质量与体验欠债。

级别问题依据与影响建议
P1 改主密钥密码后，恢复密钥实质失效 changeMasterKeyPassword() 更新了 master_key_password_hash / master_key_salt / kdf_type / kdf_params，但漏更新 recovery_backup（auth.php:436-441 对比 recoverAccount 的 auth.php:626-635）。旧恢复密钥解出的仍是旧主密钥，用它去解已用新密钥加密的 cipher 必然 GCM 认证失败 → 事务回滚 → 用户看到「找回失败，数据已回滚」，且无从自救。README 承诺「恢复密钥继续有效」在此场景下不成立。 轮换成功后同事务内重算 recovery_backup = encrypt(newKey, deriveRecoveryKey(rk, rkSalt))；或明确要求重新生成恢复密钥并在 UI 提示。
P1 SQLite 外键未启用，声明的级联不生效 连接初始化未执行 PRAGMA foreign_keys = ON（database.php:14-17），SQLite 默认关闭外键 → ON DELETE CASCADE / SET DEFAULT 全为装饰。删用户不会级联删密码、删分类不会把条目归 0（categories.php:217 注释与事实相反）。当前靠业务层前置检查规避，一旦有绕过路径即产生孤儿数据。 构造器内加一条 $this->db->exec('PRAGMA foreign_keys = ON');，并用 settings.php:check_integrity 做过一次孤儿数据体检。
P1 主密钥回传前端并随请求提交，XSS 即可全量窃取 verify_master_key 直接把 base64 主密钥放进 JSON 响应（api/auth.php:277），前端存全局 masterKey 变量并每次 decrypt 时作为参数回传（app.js:1173-1180）。同时 CSP 为 script-src 'self' 'unsafe-inline'——为注入 CSRF_TOKEN 不得不开 inline，等于给 XSS 留了门。一次 XSS = 主密钥泄露 = 全部密码泄露（即使数据盘被拿走也无法补救）。 中期改为服务端持有密钥：decrypt 接口不再接收 master_key，只从 $_SESSION 取；短期抽成 nonce 化 CSP（script-src 'self' 'nonce-...'）关掉 unsafe-inline。
P2 自动锁定（15 分钟无操作）未实现 AUTO_LOCK_TIME 在 config.php:48 定义、被 settings.php 当作默认值下发，但全库无任何消费方（前端也无计时器/失焦清 key 逻辑）。目前「锁定」只靠 SESSION_TIMEOUT=1800 的会话过期，粒度粗且不清理前端内存里的 masterKey。 前端加 visibilitychange + 空闲计时器，超时即清 masterKey 与 revealedPassword 并弹解锁框。
P2 密码历史「只写不读」 password_history 在改密时写入旧 cipher、轮换时一并重加密、永久删除时清理，但没有任何读取接口或 UI。用户看不到历史版本，表只增不减（除随条目删除），是纯成本。 补 action=history + 详情页「历史版本」抽屉；或明确砍掉写入。
P2 两组后端能力无前端入口（死接口） passwords.php 的 check_weak / check_duplicate、search.php 的 advanced、settings.php 的 stats / optimize / check_integrity —— 前端 app.js 零调用（已全量 grep 确认）。这些能力本应是密码管理器的差异化卖点（弱口令巡检、重复使用检测），目前只能手工打接口。 菜单加「安全检查」入口，一次展示弱密码数 / 重复组数 / 长期未更新数。
P2 isEncryptedCipher() 判据过宽，可能误吞明文 该函数最后一行 $isLegacy = (strlen($decoded) >= 28) 恒真，即任何能成功 base64 解码且 ≥28 字节的字符串都被判为密文（security.php:336-359）。导入时若某条明文密码恰好是 28+ 字符的合法 base64（例如长随机口令），会被当作密文直通入库 → 该条目从此解不开，且无任何报错。 判据收紧为「v3/v2 前缀正确」或「legacy 长度精确匹配 28 + N」；更稳妥是导入时对疑似密文做一次解密试探，失败则按明文加密。
P2 备份无轮转、无加密、目录权限偏松 每次登录自动备份（auth.php:731-791），文件只增不删；备份是普通 SQLite 文件（内有全部 cipher 与用户哈希），仅靠 .htaccess/Nginx 规则挡下载。data/ 与 backups/ 以 0755 创建（config.php:67-71），DB 文件沿袭系统默认 umask。 加保留策略（如保留最近 N 份 / 按天折叠）；目录 0700、文件 0600；可选对备份再做一层主密钥加密。
P2 SQLite 并发配置缺失 未设 PRAGMA journal_mode=WAL、未设 busy_timeout。多标签页或「备份/还原 + 正常读写」并发时易触发 database is locked；Database 构造器的兜底提示「可能正被占用，请稍后刷新重试」（database.php:23）正说明作者踩过。 连接后设 busy_timeout=5000 + WAL，可显著减少锁冲突（单用户场景风险低，属体验优化）。
P2 HTTP 明文部署 = 当前最大剩余风险 README 自陈：「密码管理器走 HTTP 时主密码明文过网络，是当前最大剩余风险」。代码里 cookie_secure 会随 $_SERVER['HTTPS'] 自动开关（config.php:21），但不会拒绝非 HTTPS 下的登录请求。 生产强制跳转 HTTPS（if (!HTTPS) redirect 301），或检测到非 HTTPS 时在 UI 顶部挂醒目警告条。
P2 死代码与工程欠债 Security::secureErase()、xssFilter()、会话级 rateLimit()、writeDebugLog() 均无调用方（已 grep 确认）；sessions 表只写不校验，鉴权完全依赖 PHP 原生 session；app.js 3,657 行单文件、style.css 3,442 行单文件、缓存版本号手工维护（?v=2.1.8）。另 main.php 带 UTF-8 BOM（其余 PHP 文件无），在严格 output_buffering=Off 环境下可能导致 header() 失效或页面顶部出现隐形字符。 清理死代码；拆分 JS 为 api/、render/、modals/；BOM 统一剥离。
P2 强度评分过于粗糙 checkPasswordStrength() 只有 6 条规则（长度≥6、四类字符、长度≥12），满分 6 → 「极强」（security.php:501-530）。Abc123!@ 这类 8 位常见模式可得 5 分「很强」，与真实抗爆破能力严重不符；被 check_weak / 生成器 / 注册校验共用，误判会传导到「弱密码巡检」结果。 引入 zxcvbn 类字典+模式评估（可参考其算法，不必引包），或至少加黑名单与重复/序列模式检测。
P2 单账户 + 无二次验证 注册硬限 COUNT(users)>0 即拒绝，无法多人共用；无 TOTP/WebAuthn。作为「个人保险箱」合理，但若被拿去当团队密码库会立刻不够用（无角色、无分享、无审计可见性）。 保持单账户定位即可，但应在 README 明确边界；如需扩展，先把 user_id 隔离从 SQL 里「每条都带」上升为策略层。
结论：这个项目的「安全内核」明显高于同类教程级作品的水准——KDF 参数数据化、密文版本化、迁移可回滚、限流去会话化、时序侧信道收口这五件事，通常只有在真实生产事故里被教过一遍的开发者才会做对。而它的薄弱点集中在「外围一致性」：功能做了一半的接口（历史/弱密码/统计）、声明了却没启用的约束（外键）、算了却没消费的配置（自动锁定）、更新了却没同步的字段（recovery_backup）。换句话说，核心想清楚了，边缘没收干净——这也是自研单体项目最常见的成熟度断层。
