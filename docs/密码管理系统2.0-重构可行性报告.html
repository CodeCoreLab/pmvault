二、实测坐实的缺陷（不是推断）

上一轮是基于静态阅读的推断；这一轮在 Ubuntu 上跑出来了。两条 P1 均已被真实请求复现。

2.1 P1｜改主密钥密码后，恢复密钥实质失效

复现路径（全自动，可重跑）：生成恢复密钥 → 改主密钥密码 → 用旧恢复密钥找回。

生成恢复密钥: MLNE-9XZV-BS3E-7PLC-KTLU-SGHH-ZJBB-EEPL
改主密钥结果: {"success":true,"message":"主密钥密码修改成功", ...}

改后 verify_recovery_key : {"success":true,"message":"恢复密钥验证通过"}   ← 校验通过，误导性极强
改后 recover（应能救回） : {"success":false,"message":"找回失败，数据已回滚保持原样，请稍后重试"}

根因：changeMasterKeyPassword()（includes/auth.php:436-441）更新了 master_key_password_hash / master_key_salt / kdf_type / kdf_params，唯独漏更新 recovery_backup。对照 recoverAccount()（auth.php:626-635）——那条路径是对的，还会主动刷新备份。

于是：恢复密钥解出的仍是 旧主密钥 → 用它去解已用新密钥加密的 cipher → GCM 认证必然失败 → 事务回滚 → 用户看到「找回失败」。更糟的是 verify_recovery_key 此时返回 成功（它只验能不能解出主密钥，不验主密钥还能不能解数据），用户会以为密钥有效，反复尝试后彻底失去救援手段。

危害定级：这是「唯一的账号恢复通道在用户毫无察觉的情况下被自己的一次常规操作废掉」。README 明确承诺「恢复密钥可随时重新生成…找回后恢复密钥继续有效」，与实际行为不符。修复只需在轮换事务内补一行 recovery_backup = encrypt(newKey, deriveRecoveryKey(rk, rkSalt))。

2.2 P1｜Argon2id 从未生效（常量名写错，静默降级）

README 与简介都把「Argon2id 抗 GPU 暴力破解」列为头号卖点。实测：

sodium 已加载            : YES
bestKdfType() 实际返回   : pbkdf2   ← 期望 argon2id
CONST ..._ALG_ARGON2ID   : 不存在（代码写错名）
CONST ..._ALG_ARGON2ID13 : 存在

根因：includes/security.php:51 与 :82 判定的是 defined('SODIUM_CRYPTO_PWHASH_ALG_ARGON2ID')，而 PHP 的 sodium 扩展里这个常量真实名称是 SODIUM_CRYPTO_PWHASH_ALG_ARGON2ID13。前者永不存在 → bestKdfType() 恒定返回 'pbkdf2' → 所有新用户的主密钥都走 PBKDF2-600k。

实测证据链完整：注册后库里落的是 "kdf_type":"pbkdf2","kdf_params":"{\"iterations\":600000}"；同一环境手动调用 sodium_crypto_pwhash(..., SODIUM_CRYPTO_PWHASH_ALG_ARGON2ID13) 则正常出结果（96 ms）。

为什么难发现：降级路径是静默的 —— 没有日志、没有告警，功能完全正常，只是安全强度低于宣称。这类「优雅降级遮掩配置错误」是安全类项目最典型的陷阱：降级必须配可观测信号，否则等于把缺陷藏起来。

2.3 P2｜外键确实未启用，声明的级联全是装饰

PRAGMA foreign_keys = 0  (1=开 0=关)

Database 构造器只设了 ERRMODE / FETCH_MODE（database.php:14-17），从未执行 PRAGMA foreign_keys = ON。而建表语句里写满了 ON DELETE CASCADE / SET DEFAULT，categories.php:217 还注释「级联删除由数据库处理」——与实际相反。

2.4 P2｜导入时的密文判定会误吞明文

合法base64的明文口令    len=44  => TRUE (误判为密文!)
合法base64+padding      len=44  => TRUE (误判为密文!)
普通英文短语            len=28  => false

security.php:356 的 $isLegacy = (strlen($decoded) >= 28) 恒为真，导致「任何能 base64 解码且 ≥28 字节」的字符串都被判成密文。用户若用一条 28+ 字符的随机口令（base64 字符集）做 CSV 导入，该条会被原样入库当成密文 → 此后永久解不开，且导入过程不报错。

端到端 HTTP 解锁（verify_master_key）实测 1.15 / 1.17 s（Ubuntu）、1.62 / 1.70 / 2.23 s（Windows）。一次登录必卡 1 秒以上 —— 这不是理论推演，是用户每次解锁都能感知的等待。

注意箭头方向：Argon2id（内存困难型）反而比 PBKDF2-600k 快 9 倍且更抗 GPU。也就是说，修好那个常量名，既提升安全性又让解锁快一个数量级 —— 这不是取舍，是纯赚。这条发现直接改变了重构的紧迫性排序：加密层的首位改进不是「换语言」，而是「让声明生效」。

三、重构可行性：先证明能互通，再谈换语言

重构密码管理器，最大的风险从来不是「代码写不出来」，而是「现有数据读不出来」。因此本轮先做互通性验证：用 Go 和 Rust 各自实现同一套 KDF + v3 密文格式，去解 PHP 写出的真实密文。

3.1 三语言完全互通（实测）

验证结果证据
主密钥派生一致性字节完全一致 同一 salt + 同一口令，三方派生结果：uzzdW9n7v5X19bLJvSNgsB8T1dwbxR6u0wu3yksWtq4=
PHP = Go = Rust，逐字节相同
Rust 解 PHP 密文通过 格式嗅探 v3 (AES-256-GCM + 版本前缀) → 明文 "MyStr0ng!Pass"
Go 解 PHP 密文通过 明文 "MyStr0ng!Pass"，自加密回环亦 OK
PHP 解 Rust 密文通过 Security::decrypt() 直接返回 MyStr0ng!Pass
PHP 解 Go 密文通过 同上，跨方向无差异
Go 解 PHP 新密文通过 PHP 端加密「跨语言双向互通-Go」→ Go 端正确解出
结论：v3 密文格式是「可移植事实标准」。它没有依赖任何 PHP 特有语义 —— 0x03 ‖ IV(12) ‖ Tag(16) ‖ CT 就是标准 AES-GCM 的字段重排。任何语言只要拿到 AES-256-GCM 和 PBKDF2/Argon2id 就能读写，不存在锁定。这意味着换语言不需要数据迁移窗口、不需要停机、不需要导出导入：新旧实现可以同期并存，读同一份库、写同一份库。

五、三条重构路线与推荐

推荐

A. Go 后端 + 保留现有前端

net/http + modernc/sqlite · 2 MB 单文件 · 约 2.5–4 周

做什么：用 Go 重写 api/* 8 个端点与 includes/* 5 个类，main.php/index.php 改成 Go html/template 渲染同样结构，app.js 的 apiCall 契约保持不变（只改 base path）。

为什么选它：① 实测互通已验证，可与 PHP 并行读写同一份库，零停机迁移；② 纯 Go SQLite 驱动免 CGO，实测通过；③ 一条命令交叉编译三平台，实测通过；④ 解锁从 892 ms 降到 327 ms；⑤ 语法简单，你自己能读懂改得动。

代价：Go 的模板不如 PHP 混写灵活，main.php 里 1,085 行的「HTML+PHP 混杂」需要拆成模板片段，是主要工作量。

B. Rust 核心 + Tauri 桌面端

Tauri 2 + React/Svelte · 591 KB · 约 6–10 周

做什么：Rust 层持全部密钥与加解密，前端只显示；跑成本地桌面应用而非 Web 服务。

为什么值得：① 架构上最正确 —— 消除「服务端持密钥」这一整类攻击面（Rowel 已验证这条路）；② 产物最小、内存安全编译期保证；③ 加密生态最丰富。

代价：① 失去「浏览器随时访问」的便利，手机端要另做（Tauri 2 支持 iOS/Android 但工程复杂度陡增）；② crate 拉取在内网需配 rsproxy 镜像（已实测踩到）；③ Rust 上手成本高，后续维护要靠 AI 辅助。

C. 先修不重构（推荐前置）

PHP 原地改 · 约 3–5 天 · 收益/成本比最高

做什么：修 2 个 P1（recovery_backup 同步、Argon2id 常量名）+ 4 个 P2（外键 PRAGMA、密文判定收紧、WAL+busy_timeout、备份轮转）。

为什么必须先做：这些缺陷换语言一样会带着走 —— 常量名写错、漏更新字段、忘记开外键，都是设计问题不是语言问题。重建在 Go 或 Rust 上只会让同样的坑更难发现。

额外收益：修完 Argon2id 后解锁从 892 ms 掉到 91 ms，比换 Go（327 ms）还快，性能诉求当场消失。

建议顺序：C → A（可选 B）。
先花 3–5 天把 P1 修掉并让 Argon2id 真正生效 —— 此时性能已反超任何重写方案，重构的「性能动机」自动消解。
之后若仍想换语言（为了部署简化：单文件替换 PHP 环境；或为了长期可维护性），选 A 路线，用已验证的互通性做灰度：Go 与 PHP 同时指向同一份 SQLite，先在 Go 侧只接管只读接口（列表/搜索/详情），观察一周再切换写接口，最后下线 PHP。
B 路线只在「明确要做成桌面/离线应用、且愿意放弃 Web 访问」时才值得投入。

5.1 A 路线的灰度切分（基于互通性设计）

阶段Go 侧接管验收判据
P0只读：list / get / search / categories.list与 PHP 返回逐字段 diff 为空；decrypt 仍由 PHP 处理
P1decrypt + generator + settings.stats用同一 salt 派生主密钥与 PHP 字节一致（已有验证脚本）；解锁耗时从 892 ms 降到 327 ms
P2写：add / update / delete / 分类增删PHP 读 Go 写的记录能解密，反之亦然（双向已验证）；写接口灰度期间禁推 webhook
P3backup / restore / import_exportVACUUM INTO 快照与 PHP 版一致；还原后 Database::close() 等价的连接重建逻辑
P4认证与迁移：auth / migrate / recovery老库 kdf_type 为空时的 legacy PBKDF2-10000 路径也能解（三格式识别）；recovery_backup 同步已修
P5下线 PHP 服务全量回归 + 备份验证，PHP 目录保留只读一段时间

5.2 迁移时必须守住的三个坑（实测得来）

  1. v2 / legacy 双格式不能丢：现有代码能解三种格式（v3 有前缀 GCM、v2 CBC+HMAC、legacy 无前缀 GCM）。互通验证只覆盖了 v3。移植时若只实现 v3，老用户数据会静默打不开。必须连同「按首字节构造候选列表、失败回退」那段逻辑一起搬。
  2. KDF 参数必须读库，不能写死：用户表里存着 kdf_type / kdf_params / master_key_salt。新实现要按库里的参数派生，而不是按代码里的常量 —— 否则已迁移用户会被要求重新输入，或直接解不开。
  3. Go / Rust 的 Argon2 参数语义与 sodium 不同名：sodium 用 opslimit / memlimit，Go 用 time / memory(KiB) / parallelism，Rust 的 Params 又是 (m_cost, t_cost, p_cost)。相同数字填进去结果不同。若将来启用 Argon2id，必须在库里存语义化参数名（如 {"algo":"argon2id","m":65536,"t":2,"p":1}）而非裸数字，并做一次跨实现一致性测试。

六、结论

问题答案
有可操作页面吗有。已在 Ubuntu 24.04 上跑通：登录页、初始化页、主界面、8 个 API 全部可用，注册→登录→解锁→增删改查→备份链路完整体验。
能换 Rust 或 Go 重写吗能，而且是低风险迁移。e 三语言互通已实测：主密钥字节一致，PHP/Go/Rust 密文可互相解密。v3 格式是纯标准 AES-GCM，无语言锁定。
Go + GUI 还是 Rust + GUI若目标仍是「浏览器可访问」→ Go 后端（改动最小、纯 Go SQLite、单文件交叉编译、语法可维护）。
若目标是「桌面/离线客户端 + 最高安全架构」→ Rust + Tauri（密钥不出核心，参考 Rowel；代价是失去 Web 访问、上手陡）。
两者都能做 GUI：Go 走 Wails/Fyne，Rust 走 Tauri/egui。
最该先做的事不是重构，是修 P1。Argon2id 那个常量名修好后解锁从 892 ms → 91 ms，比任何重写方案都快；恢复密钥失效那条则直接关乎「账号能否得救」。这两件事换语言也一样要修，且 PHP 里改成本最低。
GitHub 借鉴架构上最该抄 Rowel「密钥不出核心」（对应本项目 P1 主密钥回传前端）与 gopass「存储后端可插拔」（对应渐进式换语言）；功能上抄 KeePassXC 的数据库健康报告（把已有死接口接通）。
验证方法：跳板机 Ubuntu 24.04.4 上安装 PHP 8.3.6（apt，含 openssl/pdo_sqlite/sodium/sqlite3）、Go 1.23.4（dl.google.com 直装）、Rust 1.99.1（rustup + 清华镜像）；上传原始源码至 /opt/lab/pm2.0；用 curl 驱动真实 HTTP 请求完成全链路测试；用自写 Go/Rust 原型程序对 PHP 真实密文做双向解密验证。
所有数字均为本机实测（每组 3 次取样），非估算。产物留存：源码 重构验证/原型源码/，可复现脚本 重构验证/脚本/。
未验证项（明确标注）：Nginx/Apache 下的目录防护（仅在 php -S 下测到可下载）、前端 JS 交互（用 curl 测 API，未做浏览器端点击级验证）、v2/legacy 历史格式互通（库中只有 v3 数据）。
